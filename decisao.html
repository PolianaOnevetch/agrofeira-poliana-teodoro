1. As correções de acessibilidade

Correções de acessibilidade do catálogo e do formulário
Componente Problema Como se detectou Correção Onde está no código
O nome do botão do menu O nome na documentação estava em inglês "Toggle navigation". No painel Accessibility, que mostra o nome acessível do botão. Foi alterado para aria-label="Menu". No button.navbar-toggler da barra de navegação.
O nome do botão de fechar O nome na documentação estava em inglês "Close". No painel Accessibility, que mostra o nome acessível do botão. Foi alterado para aria-label="Fechar". No button.btn-close do diálogo de detalhes do açaí.
O nível do título do diálogo A documentação usa h1, mas a página já possui um título principal. Comparação com a estrutura de títulos recomendada para a página. Foi usado h2 com as classes modal-title h5. No título “Açaí médio” dentro de .modal-header.
a ligação das mensagens aos campos As mensagens de erro não estão associadas aos campos para leitores de tela. Painel Accessibility do Chrome, verificando aria-describedby e a descrição do campo. Foram adicionados IDs às mensagens e aria-describedby aos campos correspondentes. Nos campos nome, email e termos, e nas respectivas mensagens .invalid-feedback.

Pendências

  • Foco após erro no formulário: Quando o formulário é enviado com dados inválidos, o foco permanece no botão de envio, em vez de ser direcionado ao primeiro campo com erro
  • Diálogo de detalhes apenas do cartão açaí: O diálogo apresenta informações específicas do Açaí médio e não exibe detalhes dos outros produtos. Para ampliar essa funcionalidade, seria necessário implementar uma forma de atualizar o conteúdo do diálogo conforme o produto selecionado, e precisaria de JavaScript adicional.

2. O registro de decisão

Contexto

No projeto AgroFeira, é preciso escolher entre CSS autoral e Bootstrap. O CSS autoral transferiu 4,9 kB, enquanto o CSS do Bootstrap e seus arquivos de customização somaram 35 kB. O script do Bootstrap tem 80,5 kB de recurso e 25,2 kB transferidos. Sem JavaScript, o menu e o diálogo não funcionaram, e o formulário ficou sem validação.

Opções consideradas

  • Folha autoral: Oferece mais controle e personalização, transferiu 4,9 kB de CSS, mas exige mais trabalho de implementação e manutenção.
  • Bootstrap: Oferece grade e componentes prontos, mas seu CSS transferiu 35 kB e seu JavaScript, 25,2 kB. Poderia usar somente o CSS para evitar o script do framework.
  • Tailwind: Permite criar interfaces com classes utilitárias, mas exige aprender outra abordagem e configurar o processo de produção. Além disso a documentação explica que o Play CDN é usado para desenvolvimento e não para produção.

Decisão

Escolhi usar o Bootstrap somente com CSS, pois aproveito os componentes prontos e evito que o JavaScript do framework dispute o controle dos elementos com o React a partir da atividade 11.

Consequências aceitas

  • Peso maior do CSS, sendo 35 kB contra 4,9 kB
  • Implementar no React a abertura e o fechamento do menu e do diálogo, garantindo foco, navegação por teclado e atributos ARIA.

O que me faria mudar de ideia

Eu pensaria em mudar de ideia caso implementar as interações do menu e diálogo no React se torne muito mais trabalhoso e complicado do que o JS do Bootstrap
